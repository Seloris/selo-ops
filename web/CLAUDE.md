# web — Dashboard of selo sessions and projects

```component
kind: front
stack: react-express
skin: aurora
layers: [data, pages, ui]
commands:
  build: npm run build
  test: npx vitest run
  lint: npx eslint {files}
  prepare: npx openapi-typescript ../api/openapi.json --output src/api/schema.d.ts
  serve: npm run dev
  demo: npm run demo
port: 5173
demo_port: 5181
```

All commands run from this component's path. The front has no unit tests of its components: never create a `*.test.tsx`. A pure `.ts` module (no React, no DOM: a formatter, a reducer, a date rule) gets a Vitest `*.test.ts` beside it. Lint only the files a stage changed, never the whole app.

## Structure

```
src/
  main.tsx                  the theme imports first, then the React root, QueryClientProvider, RouterProvider
  router.tsx                the route tree, one lazy route per feature page
  api/
    schema.d.ts             generated by `prepare` from the API's OpenAPI document: never edited by hand
    client.ts               the openapi-fetch client (`createClient<paths>`), base URL, auth header, problem-details handling
  features/{feature}/
    data/                   query and mutation hooks over the client (`use{Entity}Query`, `use{Action}Mutation`), query keys
    pages/                  routed pages (`{Name}Page.tsx`)
    ui/                     presentational components (props in, callbacks out), forms (`{Name}Form.tsx`)
  shared/
    ui/                     shared components, one {Name}.tsx and its {Name}.module.css per element of the skin's recipes; labels are props, no className prop, no feature word
                            Panel, PageTitle, Field (label, error, the control as a render prop), TextInput, SearchInput, Select,
                            Button (variant: primary, danger, quiet, ghost), Switch, Checkbox, List (List, ListItem with isDone, ListItemText),
                            Badge, EmptyState, LoadingState, ErrorMessage (role="alert"), ConfirmDialog (a native <dialog>), icons.tsx,
                            Segmented, NavTabs (links between pages, a page not built yet dimmed with its note), IconButton, Tag (color tints it), StatusDot, Dropdown (DropdownCheck, DropdownSeparator, DropdownNote; `triggerLabel` for an icon trigger, `align="end"`), CommandBox, Drawer (a side panel), Modal (a large native dialog, open while mounted), Toast, Card (a static block on the row tokens), TextArea (the text field on several lines); Button also takes size="sm"
      theme/                fonts.ts (the skin's font imports) and skin.css (its tokens), both written by setup: never edited; base.css (the page), overrides.css (this application's values)
    lib/                    utils (formatAge, clipboard, storage, useNow), theme (data-theme on the root), notifications (the states that notify, app FR-05), flags (the flagged sessions and their switches, sessions-live FR-42, app FR-07), i18n/ (fr.json, t and tn)
```

## Package scripts

| Script | Does |
|---|---|
| `build` | `tsc -b && vite build`: type-checks, then bundles |

## Conventions

- **TypeScript strict**, function components, hooks; no default exports except where React Router's lazy routes need them; no `any`.
- **Data:** a page uses its feature's `data/` hooks; the hooks are the only place that calls the API client; the client is the only place that calls `fetch`. Server state lives in TanStack Query (one query-key factory per feature, every mutation invalidates or updates the queries it changes); local UI state in `useState`/`useReducer`; no global store unless several features share client state.
- **Across features:** the projects page reads the sessions' query (`useSessionsQuery`, the same cache) and their pure helpers (`sessionText.ts`, `panelWidth.ts`) for its live sessions and its panel; the app shell's notifier (`useStateNotifier`, app FR-05) reads the same query, `stateAlerts.ts` and `sessionText.ts` (a `data` hook reading a `ui` helper, for the notification's labels); the sessions page reads the projects' query (`useProjectsQuery`, enabled only while its « Nouvelle session » window is open, sessions-live FR-44); the app shell opens the help's popup (`HelpDialog`) and the settings window (`SettingsDialog`, with its `settings` data hooks, app FR-08): the only imports from another feature.
- **Types** of requests and responses come from `src/api/schema.d.ts` (`paths`, `components["schemas"][...]`), never redeclared by hand.
- **Pages** are routed, thin, and compose UI components; **UI** components receive props and emit callbacks: no data hook, no client call inside them.
- **Forms:** one `{Name}Form.tsx` per form, holding its fields, validation and the mapping of the API's problem details (`400` field errors) to field messages.
- **i18n:** every user-facing string goes through the translation layer; keys live in `src/shared/lib/i18n/{lang}.json`, named `{feature}.{element}.{text}`; a missing key is a review finding.
- **Styling:** CSS Modules (styles scoped to their component; no global style outside `src/shared/ui/theme/`). Styles read the skin's variables only: no literal color, radius, shadow, font family or control height (see Design).
- **Loading and errors:** every page that reads data shows a loading state and an error state; a failed mutation shows the problem details' message.
- File naming: `PascalCase.tsx` for components and pages, `camelCase.ts` for hooks and utils (`useOrdersQuery.ts`).

## Design

The skin named in the `component` block above: its fonts in `src/shared/ui/theme/fonts.ts` and its tokens in `skin.css` beside it (both written by setup, rewritten by `/selo:setup skin`), imported first by `main.tsx`, then `base.css` and `overrides.css`. The UI follows the selo plugin's design rules (`reference/ui-design.md`), its element recipes (`skins/recipes.css`) and the skin's `SKIN.md`, read in place; this section wins over them. Features compose the `shared/ui` components and style only their own layout; a recipe or a component two features need that `shared/ui` lacks is added there, in the same way.

- Variables this application changes: in `src/shared/ui/theme/overrides.css`, never in `skin.css`.
- Rules this application adds or replaces: here, one line each.
- State colours: amber (`--warn`, `--warn-soft`, added in overrides.css) and rose (`--danger`) mark only what waits on the person, and the detail's « Archiver » and « Désarchiver » buttons, kept in sight; a flagged session's flag takes its own bright yellow (`--flag`, sessions-live FR-42), never amber; the other states keep one colour each (sessions-live FR-10): blue `--working` for a running session, `--done` green for a finished job (a hollow ring of it for an ended turn), a hollow grey for a closed or archived one; everything else stays neutral, except the section hues (`--hue-*`, below) and the lane tokens (`--lane-*`: `--lane-free` slate, fastlane lime, blueprint teal, pilot violet) of the help (help FR-11), which also colour a session's type of work (FR-29); the help's titles carry a short rule in the three lane colours, as a decoration.
- The session detail's section headings carry an icon on a soft tint of their own hue (`--hue-close`, `--hue-recap`, `--hue-agents`, `--hue-files`, `--hue-usage` for the usage section with the gauge icon, `--hue-trail` for « Déroulé du tour », `--hue-next` for « Action suivante », also its chip in the list and its button there once it copied, the only violet of the page, in overrides.css), « Ce qui est attendu » the tint of its state, the settings neutral; the file tree's folder icons take `--hue-files`; these hues mark a section, never a state.
- The projects page: one `--bp-*` token per blueprint state (projects FR-14), the same in bars, legends, tags and tracks, and its section headings' icons on their own hues (`--hue-progress`, `--hue-blueprints`, `--hue-specs`, `--hue-ideas`, `--hue-debt`), in overrides.css; a delta's figures, bar and signs take their own tokens (`--delta-add` green, `--delta-change` yellow, `--delta-remove` red), never a state colour.
- Mint (`--accent`) only for the active setting, checked boxes and the « Ouvrir » action.
- Theme: Clair / Sombre chosen in the header, Sombre by default; overrides.css restates both palettes under `:root[data-theme]`, so a new token needs its light and dark values there.
- Commands, branches and commit subjects in `--font-mono` (added in overrides.css).

## Testing

- No unit tests of components: the `try` skill checks a change in the real app, on this worktree's slot. Pure `.ts` modules (sorting, grouping, formatting) have Vitest tests beside them (`npx vitest run`).

## Local run

- Prerequisites: Node 22, `npm ci`.
- Run: `/selo:run` starts the API, then the front, on this worktree's slot (http://localhost:5173 on slot 0, the port + 10 per slot); `npm run app` at the root does the same outside a session. `npm run dev` alone serves http://localhost:5173 and expects the API on http://localhost:3000.
- Demo: `npm run demo` → http://localhost:5181 (slot 0; `/selo:run — demo` on this worktree's slot), proxied to the API's demo on port 3101, with `--force` (no stale Vite cache). `try` starts both demos and stops them after the test.
- `prepare` regenerates `src/api/schema.d.ts` from the API's committed handoff file; run it at the start of every front stage.
